# 待处理改进

外部贡献者提交的**改进提案**落在这里。

这些不是改动，是「该改什么」的说明——提交时打包成一个 PR，由合伙人核实后改到
对应技能里。已经改好文件的走另一条路：`python contribute.py --from-installed`，
那个产生的是真实 diff，不进这个目录。

## 文件命名

`<日期>-<技能名>-<类型>.md`，例如 `2026-10-30-天信税务申报-政策过期.md`。
由 `contribute.py --proposal` 自动生成，手工放进来也行，照这个格式起名就好。

**日期写在开头是有用的**：`--list` 和 `check.py` 都靠它算提案搁了多久。

## 处理节奏

| 环节 | 怎么走 |
|---|---|
| **谁看** | 合伙人。提案一律以 PR 形式进来，PR 有通知，不会悄悄堆着 |
| **什么时候处理** | 就着 PR 一起。看到 PR 就顺手处理，不另设「集中处理日」 |
| **采纳** | 改动落到技能里，删掉提案文件，PR 提交信息写清「采纳 xxx 提案，改到 `税务/天信税务申报skill/references/01-…`」 |
| **不采纳** | 删掉提案文件，在 PR 里说明理由。让人知道自己提的东西被看过、为什么没采纳 |
| **多久算拖太久** | 30 天。`--list` 会标 ⚠，`check.py` 第 9 项会提醒 |

**关键是别让它变成死目录。** 提案放着不管的代价不是占地方，是**提的人看不到回音，
后来的人更不想提**——反馈机制一旦给人「提了也没用」的印象，就再也收不回来了。

所以这份文件里最重要的一条是：**处理完就删**。提案的价值在于被执行，
执行完留着它只是噪音。不采纳也一样——删掉，但在 PR 里说清楚为什么。

## 看有哪些待处理

```bash
python contribute.py --list
```

列出技能、类型、搁了多久，超过 30 天的标 ⚠ 并给出处理建议。
`python check.py` 的第 9 项也会查这一项。

## 提案里有什么

模板在 [`../templates/改进提案.md`](../templates/改进提案.md)。核心两栏：
「现在怎么写的」（原文照抄）和「应该是」（改成什么）。
**政策类改动必须给文号**，没有文号的税率、优惠比例一律不收。
