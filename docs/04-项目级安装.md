# 方式三 · 项目级安装

技能装进某个项目的目录，只在那里面生效。

---

## 步骤

```bash
cd tianxin-skills
python install.py --project /path/to/你的项目
```

装完的技能在：

```
/path/to/你的项目/
└── .workbuddy/
    └── skills/
        ├── README.md              安装器写的来源说明
        ├── 天信文档与报告/
        ├── 天信日报/
        ├── 天信实务知识库/
        └── 陈版主实务问答/
```

在这个目录下开对话，四个技能才会被加载。

---

## 什么时候用这个

**客户项目专用配置。** 比如一个长期服务的尽调项目，规范跟着项目仓库走，`git clone` 下来就带着。换电脑不用重新配。

**多人协作。** 全局安装是「这台机器上当前用户的」，一个人装了旧版不会影响别人；项目级安装跟着仓库走，谁 clone 谁得到同一份规范，不会出现「他用新版我用的旧版」。

**不想污染其他项目的对话。** 有些项目的上下文很紧（比如代码项目），不希望里面混进「陈版主怎么说」这类能力。项目级隔离掉。

---

## 和全局安装的关系

两边都装了同名技能时，**项目级优先**。

实际上多数 agent 的加载顺序是：项目级 skills 先加载，用户级 skills 后加载，同名以先加载的为准。如果发现行为不对，先检查是不是两边都装了。

---

## 多项目

同一个技能装进多个项目，会有多份副本。更新要逐个跑：

```bash
for proj in /path/to/项目A /path/to/项目B /path/to/项目C; do
  python install.py --project "$proj" --force
done
```

**不要做成软链接**。看着省事，实际两个问题：一是很多工具的 skill 扫描不跟随符号链接；二是 Windows 上 junction 换机器就断。

---

## 审查装了什么

```bash
python install.py --verify --project /path/to/你的项目
```

---

## 卸载

```bash
rm -rf /path/to/你的项目/.workbuddy/skills
```

如果项目里还有别的技能混在同一个目录，只删这四个：

```bash
for d in 天信文档与报告 天信日报 天信实务知识库 陈版主实务问答; do
  rm -rf "/path/to/你的项目/.workbuddy/skills/$d"
done
```

---

## 该不该把 `.workbuddy/skills/` 提交进仓库

看情况：

| 情况 | 建议 |
|---|---|
| 团队共用一套规范，希望版本一致 | **提交**。顺手在 README 写清版本号 |
| 项目对外开源，或者客户会看到仓库 | **不提交**。加到 `.gitignore`，在 README 写一行「需要时跑 `install.py --project .`」 |
| 只是自己用 | 不提交。`git status` 里天天看到一堆技能文件很烦 |

不提交的话，加这一行到 `.gitignore`：

```
.workbuddy/skills/
```

---

## 一个细节

装项目级时，安装器会在 `<项目>/.workbuddy/skills/README.md` 写一份清单，记着来源、安装时间、本次装了哪几个、怎么更新。

这份文件是给人看的，也是给下一个接手的人看的——半年后没人记得这些技能哪来的。
