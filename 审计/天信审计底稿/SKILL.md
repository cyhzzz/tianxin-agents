# 天信审计底稿

我是天信审计项目的"作业台"。判断层的方法论（风险导向四步走、六步 SOP、五道防线、监管清单）已由「天信实务知识库」的四张审计卡讲透，本技能**不重复判断**，只解决一个县城所天天被卡住的问题：

> 计划怎么写、风险怎么落到纸上、函证发几家怎么控制、监盘记录写什么、抽样抽多少、底稿怎么编索引、什么时候能出报告、质控页谁签字。

这些每个所的做法都不一样，天信用自己的模板。

## 一、本技能与判断层的关系（别重复造轮子）

| 你需要 | 去哪 |
|---|---|
| 风险导向骨架、重要性口径、四程序"为什么做"、意见判定树 | `天信实务知识库` → `cards/audit-core.md` |
| 六步流水线、交付清单总控 | `cards/audit-sop.md` |
| 监管处罚五道防线（收入/函证/存货/持续经营/减值） | `cards/penalties.md` |
| 监管提示三张清单（独立性/舞弊 8 领域/合规底线） | `cards/reg-tips.md` |
| **本技能：上述"判断"对应的天信作业模板与底稿** | 本目录 `references/` |

## 二、工作流（对应 GOA 会计报表审计专家能力）

GOA 专家的核心交付 = 审计计划 / 风险评估 / 审计程序 / 工作底稿 Checklist。本技能把它拆成天信作业闭环：

1. **审计计划**（接 `audit-core` 的 R+M）→ `references/01-审计计划模板.md`：准则适用、时间人员、风险清单、重要性计算、总体策略。
2. **风险评估工作底稿**（接 `audit-core` 的 R）→ `references/02-风险评估工作底稿.md`：了解被审计单位问卷、风险识别矩阵、舞弊风险识别。
3. **进一步审计程序（四程序）作业 Checklist**（接 `audit-core` 的 P）→ `references/03-四程序作业Checklist.md`：函证（控制+替代）、监盘（计划+记录+影像）、截止、分析；抽样量见 `references/04-抽样量指引.md`。
4. **底稿索引体系** → `references/00-底稿索引体系.md`：天信自己的编号/分类（A–H 类）。每个所不同，这是天信的。
5. **报告与质控工作底稿**（接 `audit-core` 的 O + `penalties`/`reg-tips`）→ `references/05-报告与质控工作底稿.md`：意见判定表、强调/持续经营段决策、质控复核签字页。

## 三、上手方式

拿到一户审计任务，按上面 1→5 顺序走，每一步打开对应 reference 复制模板填。常用表格（函证清单、抽样表、监盘表、截止测试表、调整分录汇总表）统一在 `references/06-常用表格模板.md`。

## 四、红线（沿用项目 AGENTS.md，逐条适用）

- **事实与推演分离**：底稿里客户提供的数标【事实】，我们测算/估计的标【推演】，不混写。
- **不编造准则与处罚**：引用 `audit-core` / `penalties` / `reg-tips`，不杜撰文号、比例、案例；记不清就让使用者查原文或调「陈版主实务问答」Skill（`chenyiwei-bbs`）。
- **不替代 CPA 判断**：本技能出模板、Checklist、索引；结论、抽样最终量、意见类型、签字由项目注师负责。所有产出默认带「待复核」。
- **红线即作业项**：`penalties` 五道防线、`reg-tips` 三张清单不是"读读而已"，要落进对应底稿和质控页逐项勾。
- **底稿索引必须连续可追溯**：无索引 = 没做（监管处罚高频源于程序没做/没留痕）。

## 五、出版物

底稿/报告最终排版走「天信文档与报告」Skill 的四轨（Word / A4 PDF / 网页长页 / 演示 deck）；本技能只负责内容骨架与勾稽，不负责版式。

## 反馈与改进

这份技能是 [cyhzzz/tianxin-agents](https://github.com/cyhzzz/tianxin-agents) 的**副本**。
**你在这里的修改不会自动回到仓库**——会话一结束就没了。

遇到下面任一情况，请留下改进提案，不要只在会话里绕过：

- 内容有误、政策已变、数字对不上
- 缺了某一类常见情形，你只能临场发挥
- 用户纠正了你，而纠正的内容本该写在这份文件里

### 优先：能改就直接改文件，再回传

AI 遇到技能有问题，默认做法是临场绕过——这次能用，下次还是错的。
**更好的做法是直接改 `~/.workbuddy/skills/天信审计底稿/` 下的文件**，然后告诉用户：

> 我改了「天信审计底稿」里的 `references/xx-yyy`，改动还没回仓库。
> 克隆 https://github.com/cyhzzz/tianxin-agents 后跑这一条就能提 PR：
> `python contribute.py --from-installed ~/.workbuddy/skills/天信审计底稿`

这条路径最有用——它产生的是**可以逐行 review 的真实改动**，不是一段描述。

### 改不了时才交提案

政策拿不准、超出权限、只是觉得表述不清——写成文件再告诉用户：

    # 改进提案：天信审计底稿 · 内容有误

    | 字段 | 内容 |
    |---|---|
    | 技能 | 天信审计底稿 |
    | 类型 | 内容有误 |
    | 位置 | references/xx-yyy.md 第 12 行 |

    **现在怎么写的**：（原文照抄，别转述）
    **应该是**：（改成什么）
    **依据**：（政策文号 / 准则条款）

存到 `~/.workbuddy/skills/_待提交改进/天信审计底稿-<主题>.md`，然后告诉用户跑
`python contribute.py --proposal <该文件>`。没有 git 也能反馈——
去仓库开 issue 把上面这段贴进去就行。

**政策类改动必须给文号。** 没有文号的税率、优惠比例一律不收：
一份过期税率表会让客户少缴、补税加滞纳金，这种错仓库里出过六处。
**提案里不要写客户名、税号、金额**——那是公开仓库。
