# 09 控制测试底稿

> 天信原创。原 `references/00-底稿索引体系.md` 只把"控制测试"列成一个类目，一句带过——真做的时候没人知道底稿长什么样。
> 参数（重要性、风险模型、抽样矩阵）另见 `上游/cpa-6-重要性与审计参数.md`；本文件补的是**底稿结构与判定逻辑**。

## 一、什么时候必须做控制测试

不是每户都要做。出现下列情形才做：

- 拟**信赖内部控制**，以减少实质性程序（否则直接做实质性程序更省）
- 连续审计且内控未变，需**每年至少测试一部分**（不能凭上年结论免做）
- 高风险领域（收入确认、资金、关联方交易）且内控是关键防线
- 集团审计中，组成部分由他人执行，需评价其控制

**做了就必须做完**：测了控制又不用结论，等于白花工时；不打算信赖，就别测。

## 二、了解内控：五要素都要留痕

| 要素 | 记录什么 | 底稿形式 |
|---|---|---|
| 控制环境 | 治理结构、管理层理念、诚信与道德、权责分配、人力资源政策 | 问卷 + 访谈记录 |
| 风险评估过程 | 客户怎么识别与应对经营风险 | 风险清单 |
| 信息系统与沟通 | 用的什么系统（财务软件/进销存）、谁有权限、账怎么生成 | 系统截屏 + 权限表 |
| **控制活动** | 授权审批、职责分离、凭证与记录、实物控制、复核与对账 | **控制矩阵（核心底稿）** |
| 对控制的监督 | 内审、管理层复核、差异分析 | 会议记录/复核签字样本 |

**关键一句**：小客户往往"老板一支笔"，实质是**没有控制**或**控制由一个人执行**——这时如实写"控制不可信赖，转实质性程序"，别硬凑一套看着漂亮的控制矩阵。

## 三、穿行测试（选 1–2 笔，走完全流程）

目的：确认"我们理解的控制"确实是"实际运行的控制"。

做法：挑一笔已完成的交易，从**原始单据**走到**报表数**，每个环节问"谁做的、谁批的、留了什么证据"。

- 采购：请购 → 审批 → 订单 → 验收 → 入库 → 发票 → 付款 → 入账
- 销售：订单 → 审批 → 发货 → 开票 → 收款 → 入账 → 对账
- 薪酬：考勤 → 编制工资表 → 审批 → 发放 → 社保申报 → 入账

穿行测试留痕：单据清单（编号、日期、金额、经办人、审批人）+ 结论（控制是否如描述运行）。

## 四、控制测试的四种方法

| 方法 | 适用 | 弱点 |
|---|---|---|
| 询问 | 了解，不单独作为测试证据 | 只能作补充 |
| 观察 | 职责分离、实物控制（如仓库收发） | 只能证明"看的时候是这样" |
| 检查 | 审批签字、复核痕迹、系统日志 | 最常用 |
| **重新执行** | 关键计算、对账、系统逻辑 | 最有力，工时高 |

**测试要针对"控制点"，不是针对"结果"**。检查一张有签字的凭证，证明的是"审批控制运行过"，不是"这笔业务真实"。

## 五、样本量（参考下限，非强制）

| 控制运行频率 | 全年次数（约） | 建议样本量 |
|---|---|---|
| 每年 1 次（如年度盘点审批） | 1 | 1 |
| 每季 | 4 | 2 |
| 每月 | 12 | 2–3 |
| 每周 | 52 | 5 |
| 每日 | ≈250 | 20–25 |
| 每笔交易（自动化/人工逐笔） | 大量 | 25–40，或按抽样表 |

自动化控制（系统强制校验、权限控制）样本量可显著降低（**1 笔 + 系统逻辑说明 + IT 一般控制评价**），但需确认系统本期未变更。

## 六、偏差怎么评价（这一步最容易被跳过）

- 记录每一个偏差：哪笔、什么环节、谁、为什么、是否已纠正。
- 判断偏差性质：**孤立偏差**（人为疏忽）还是**系统性偏差**（控制设计本身有缺陷）。
- **偏差率**：偏差数 ÷ 样本量。超过可容忍偏差率 → 控制不可信赖 → **扩大实质性程序**，不得"再多抽几笔看看能不能凑过去"。
- 发现舞弊迹象的偏差：不论比例，一律上报，并评估对整份审计的影响。

## 七、底稿格式（控制矩阵，一页一个循环）

| 控制编号 | 控制描述 | 所属循环 | 相关认定 | 测试方法 | 样本量 | 偏差数 | 结论 |
|---|---|---|---|---|---|---|---|
| C-SL-01 | 销售订单须经销售经理审批后方可发货 | 销售与收款 | 发生、准确性 | 检查（审批签字） | 25 | 1 | 有效（偏差已追查） |
| C-SL-02 | 每月末由财务经理核对发货单与开票明细 | 销售与收款 | 完整性、截止 | 重新执行 | 3 | 0 | 有效 |
| C-CG-01 | 付款须经老板与财务双签，网银 U 盾分离保管 | 采购与付款 | 存在、权利 | 检查 + 观察 | 25 | 0 | 有效 |
| C-XC-01 | 工资表由人事编制、财务复核、老板审批 | 薪酬 | 准确性、发生 | 检查 | 3 | 0 | 有效 |

矩阵后面必须附：控制描述对应**认定**的理由、样本选取方式（随机/系统/判断）、偏差说明、结论对实质性程序的影响。

## 八、控制无效之后怎么办（结论要落到程序上）

| 情形 | 应对 |
|---|---|
| 控制设计有效但未运行 | 视为不可信赖，转实质性程序，扩大样本 |
| 控制设计本身有缺陷 | 记入管理建议书；实质性程序不得依赖该控制 |
| 仅个别偏差 | 追查偏差原因，评估同类交易影响，必要时扩大实质性程序 |
| 舞弊相关 | 上报合伙人，重新评估风险，考虑对报告的影响 |

## 九、常见错误（监管挑得最狠的几处）

1. **控制矩阵是抄的**——描述与客户实际不符，穿行测试一看就露。
2. **测了控制不留样本清单**——只写"抽查 25 笔，未发现异常"，没有笔号、日期、金额。
3. **偏差不记录**——只写结论"有效"，抽样表里却有红笔。
4. **控制结论与实质性程序脱节**——控制判定无效，实质性程序却没加量。
5. **连续审计照抄上年底稿**——本期控制已变（换系统、换人），底稿原样搬。

> **红线**：控制测试底稿的用处是"证明我们不是凭感觉少做了程序"。少做可以，但必须**有依据地少做**。
